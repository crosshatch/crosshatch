# Effect HTTP

Effect HTTP integrations expose paid resources through ordinary HTTP routes.

## Route Boundary

Place the x402 boundary at the route that owns the paid resource. If payment is missing, return a `402` with a payment
requirement. If payment is present, verify it before continuing to the handler.

## What The Route Owns

The route should own four decisions:

- which resource is being requested
- how that resource is priced
- which x402 requirement is returned when payment is missing
- whether an incoming payment payload is valid before paid work starts

Keep those decisions close to the route so the payment boundary is visible in traces, logs, and code review.

## Flow

::::steps

### Receive The Request

Read the ordinary application inputs first: path params, query params, body fields, authenticated user context, and any stable
resource identifier your service uses for reconciliation.

### Price The Resource

Compute the x402 requirement before doing expensive work. The requirement should be specific enough for the client to pass
directly to Crosshatch.

```ts
import { Asset, Micros, required } from "crosshatch"

const priceResource = ({ resourceId, treasury }: { readonly resourceId: string; readonly treasury: `0x${string}` }) =>
  required({
    url: `https://merchant.example/resources/${resourceId}`,
    description: `Access resource ${resourceId}`,
    amount: Micros.fromInt(1),
    recipient: treasury,
    asset: Asset.BASE_USDC,
  })
```

### Return A 402 When Payment Is Missing

If the request does not include a payment payload, return `402 Payment Required` with the requirement.

```ts
const payment = request.headers.get("PAYMENT-SIGNATURE")

if (payment === null) {
  return Response.json(requirement, { status: 402 })
}
```

### Verify Before Paid Work

Only execute the paid handler after the payload has been settled or verified against the requirement. The current helper
surface exposes `settle({ payload })`, which delegates to the Crosshatch facilitator and returns the settlement network and
transaction on success.

```ts
const settlement = yield* settle({ payload })
```

### Serve The Resource

Once verification succeeds, continue to the ordinary route handler and return the paid resource.

## Route Sketch

This sketch shows the shape to preserve in an Effect HTTP route. Decoding the base64 header into `Payload.Payload` is shown
as a placeholder because most apps will centralize it in middleware.

```ts
import { Payload } from "@crosshatch/x402"
import { Asset, Micros, required, settle } from "crosshatch"
import { Effect, Encoding, Schema } from "effect"
import * as Boundary from "liminal-util/Boundary"

const decodePaymentHeader = (payment: string) =>
  Encoding.decodeBase64String(payment).pipe(
    Effect.fromResult,
    Effect.map(JSON.parse),
    Effect.flatMap(Schema.decodeUnknownEffect(Payload.Payload)),
  )

const servePaidResource = (treasury: `0x${string}`) => (request: Request) =>
  Effect.gen(function* () {
    const resourceId = new URL(request.url).searchParams.get("id") ?? "default"
    const requirement = required({
      url: `https://merchant.example/resources/${resourceId}`,
      description: `Access resource ${resourceId}`,
      amount: Micros.fromInt(1),
      recipient: treasury,
      asset: Asset.BASE_USDC,
    })
    const payment = request.headers.get("PAYMENT-SIGNATURE")

    if (payment === null) {
      return Response.json(requirement, { status: 402 })
    }

    const payload = yield* decodePaymentHeader(payment)
    yield* settle({ payload })

    const resource = yield* loadResource(resourceId)

    return Response.json(resource)
  }).pipe(Boundary.span("merchant.effect-http.serve-paid-resource", import.meta.url))

```

## Operational Model

The handler should make pricing and verification observable. Payment failures, invalid payloads, and successful settlement
are all useful events when debugging production traffic.

Useful span attributes include:

- `crosshatch.resource.id`
- `x402.requirement.id`
- `x402.payload.id`
- `crosshatch.payment.amount`
- `crosshatch.payment.asset`
- `crosshatch.payment.network`
- `crosshatch.verification.result`

Prefer stable IDs, hashes, and verification results over raw signed payloads. See [OpenTelemetry](/merchants/opentelemetry)
for the broader trace shape.

## Failure Cases

Return `402` when payment is missing or invalid. Return ordinary application errors only after payment verification has
succeeded and the paid handler has begun.

Common cases to handle explicitly:

- missing `PAYMENT-SIGNATURE`
- malformed payment payload
- payload for the wrong requirement
- unsupported network or asset
- expired or already-spent payment
- facilitator or settlement failure
