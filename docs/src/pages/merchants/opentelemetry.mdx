# OpenTelemetry

OpenTelemetry lets merchants connect payment activity to the traces that already describe resource requests, background
work, and settlement calls.

## Why Trace Payments

Payments are part of the request lifecycle. When a paid resource fails, the useful debugging question is rarely just "did
payment fail?" It is usually where the request moved through pricing, requirement creation, payload verification,
facilitation, settlement, and resource delivery.

Tracing those steps together makes it possible to answer questions like:

- Which request produced this payment requirement?
- Which payment payload paid for this resource?
- Did verification fail before or after facilitator interaction?
- Was the resource served after payment verification succeeded?
- Which settlement strategy was used for this purchase?

## Trace Shape

A typical paid request should be traceable as one connected flow.

::::steps

### Receive The Request

The merchant receives a request for a paid resource.

### Price The Resource

The merchant decides which x402 payment requirement applies.

### Emit A Requirement

If payment is missing, the merchant returns `402 Payment Required` with the requirement.

### Verify The Payload

The client retries with a payment payload. The merchant or facilitator verifies it.

### Settle Or Record Usage

The system settles immediately, records granular usage, or updates a deposit + rebate session.

### Serve The Resource

The merchant returns the paid resource.

::::

## Correlation Attributes

Use stable identifiers rather than full sensitive payloads. Useful span attributes include:

- `x402.requirement.id`
- `x402.payload.id`
- `crosshatch.purchase.id`
- `crosshatch.resource.id`
- `crosshatch.facilitator.id`
- `crosshatch.settlement.strategy`
- `crosshatch.payment.amount`
- `crosshatch.payment.asset`
- `crosshatch.payment.network`
- `crosshatch.verification.result`

Prefer IDs that can be used to look up richer state in your own systems when needed. Avoid putting secrets or large signed
payloads directly into traces.

## Effect Integration

Effect services should wrap payment boundaries in spans so payment events can be correlated with the source route or RPC
method.

```ts
import * as Effect from "effect/Effect"
import * as Boundary from "liminal-util/Boundary"

const servePaidResource = Effect.gen(function* () {
  // Price the resource, verify the payment payload, and serve the result.
}).pipe(Boundary.span("merchant.serve-paid-resource", import.meta.url))
```

For HTTP integrations, place the span around the route-level payment boundary. For RPC integrations, place it around the
paid method implementation.

## Privacy

Do not record private keys, wallet secrets, raw credentials, or user-sensitive wallet metadata. Be careful with full signed
payment payloads: prefer compact IDs, hashes, or verification results unless the payload is explicitly safe to store in
your telemetry backend.

## Where This Fits

OpenTelemetry does not change the x402 protocol. It makes the system observable by connecting requirements, payloads,
verification, settlement, and resource delivery into one operational timeline.
